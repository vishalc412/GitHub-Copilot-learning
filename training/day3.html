Session 1 — Agent Mode Deep Dive

Autonomous, multi-step editing inside your IDE

09:15–10:15 · 60 min

Reference: copilot-instructions/agents/01-agent-mode.md

ModeScopeAutonomyBest For
AskRead-onlyNone"Explain this regex"
EditFiles you addEdits onlyPrecisely scoped multi-file edits
AgentWhole workspaceFull — reads, edits, runs commands, self-corrects"Add pagination and update the tests"

Key lesson: Agent Mode rewards goals with acceptance criteria, not step-by-step instructions.

Context: Users report the login form submits twice on double-click.
Goal: Fix the race condition.
Constraints: Don't change the public API of the LoginForm component.
Definition of done: A test reproduces the double-submit bug and passes;
                     the existing auth test suite still passes.
🧪 Exercise 9.1 — Your First Agent Mode Task

Run the prompt above (or an equivalent from your own codebase) in Agent Mode. Record: which files it opened before editing, whether it asked before running terminal commands, and whether it self-corrected after a failing test.

🛡️ Guardrails to Show Live
  • Terminal command approval prompts
  • Per-file diff review before accepting
  • The undo checkpoint after a full agent turn
  • How .github/copilot-instructions.md and .github/instructions/*.instructions.md reduce bad edits

Session 2 — The Coding Agent

Issue in, pull request out — while you do something else

10:30–11:45 · 75 min

Reference: copilot-instructions/agents/02-coding-agent.md

This is fundamentally different from Agent Mode: it runs remotely, asynchronously, in an isolated environment, and pushes commits to its own branch — like assigning work to a teammate.

⚙️ Environment Setup — Do This First

Before assigning any issue, verify .github/workflows/copilot-setup-steps.yml exists and the job is named exactly copilot-setup-steps — this is what GitHub runs to bootstrap the agent's environment (install deps, set up databases, etc). This repo ships a working example.

The Strong Issue template — the single biggest lever for agent PR quality:

## Problem
[what's happening, with reproduction steps]

## Expected behavior
[what should happen instead]

## Suggested approach
[optional — a nudge in the right direction]

## Acceptance criteria
- [ ] Specific, checkable criterion 1
- [ ] Specific, checkable criterion 2
- [ ] Existing tests still pass
🧪 Exercise 9.2 — Delegate a Real Issue
  1. Write an issue using the template above, for a genuinely small task in your sandbox repo
  2. Assign it to Copilot
  3. Time: minutes to first commit, number of review rounds until mergeable
  4. Review the draft PR exactly as you would a junior teammate's — comment inline, let it push fixes
Good FitBad Fit
Well-scoped bug fixes with repro stepsVague "improve performance" asks
Adding tests to well-understood codeNovel architecture decisions
Mechanical refactorsSecurity-sensitive auth/crypto without expert review

Session 3 — Custom Chat Modes

Give the agent a job title, not just a task

12:45–13:45 · 60 min

Reference: copilot-instructions/agents/03-custom-chat-modes.md · working examples: .github/chatmodes/architect.chatmode.md, .github/chatmodes/reviewer.chatmode.md

---
description: "Plans changes without editing files"
tools: ["search", "usages"]
---

You are a staff engineer doing technical planning. Given a feature request:
1. Identify affected files and modules
2. List design options with tradeoffs
3. Recommend one approach
4. Output a step-by-step implementation plan

Never edit files directly. Your output is a plan, not a diff.

Why restrict tools per mode: the single biggest source of "the agent did something I didn't want" is giving it more capability than the task needs. This is the principle of least privilege applied to agents.

🧪 Exercise 9.3 — Ship a Team Persona

Design a custom chat mode for a role your team actually needs (e.g. "Migration Assistant" restricted to migrations/, always generating a rollback script). Have a teammate use it and report back.

Session 4 — MCP & Extensions

Give the agent eyes on your real systems

13:45–14:45 · 60 min

Reference: copilot-instructions/agents/04-mcp-integration.md, 05-extensions.md · working example: .vscode/mcp.json

{
  "servers": {
    "postgres": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": { "DATABASE_URL": "${input:database_url}" }
    }
  },
  "inputs": [
    { "id": "database_url", "type": "promptString",
      "description": "Postgres connection string", "password": true }
  ]
}
🔐 Security Checklist — Cover Before the Hands-On
  • Use a read-only DB role/connection for any database MCP server
  • Never hardcode credentials in mcp.json — use the inputs prompt mechanism
  • Keep "confirm before running" enabled for write-capable tools
  • Only install MCP servers/extensions from trusted sources
🧪 Exercise 9.4 — Connect an MCP Server

Register a local read-only SQLite/Postgres MCP server against a sandbox database. Ask Agent Mode: "What columns does the orders table have, and write a function that queries orders by customer_id using our existing DB client pattern." Watch whether it inspects the schema via the tool before writing code.

MCP vs. Extensions, in one line: MCP is what you wire up for your project's own tools; Extensions are published, org-installable integrations from vendors (or your platform team) invoked with @extension-name.

Session 5 — Multi-Agent Workflows

Treat Copilot's surfaces as a team of specialists

15:00–16:15 · 75 min

Reference: copilot-instructions/agents/07-multi-agent-workflows.md

                     ┌─────────────────────────┐
                     │   YOU (orchestrator)     │
                     └────────────┬────────────┘
                                  │
        ┌─────────────────────────┼─────────────────────────┐
        ▼                         ▼                         ▼
┌───────────────┐       ┌───────────────┐        ┌───────────────┐
│ Coding agent   │       │ Coding agent   │        │ IDE Agent Mode │
│ (Issue #101)   │       │ (Issue #104)   │        │ (you, live)    │
└───────────────┘       └───────────────┘        └───────────────┘

Pattern 1 — Fan-Out

Independent, well-scoped issues assigned to the coding agent in parallel. Each gets its own isolated branch — no collisions.

Pattern 2 — Pipeline

Architect mode plans → coding agent builds → Reviewer mode critiques the diff before a human ever looks at it.

Pattern 3 — Human-in-the-Loop

Checkpoint after the first pass before letting the agent continue — for higher-stakes changes.

Pattern 4 — Specialist Ensemble

Split a cross-domain task into sub-issues (migration, API, frontend) with explicit merge order.

🧪 Exercise 9.5 — Fan-Out Batch

Pick 3 small, genuinely independent issues. Write each with the Strong Issue template, assign all 3 to Copilot at once, and time how long until all 3 have reviewable draft PRs.

Failure ModeFix
Merge conflicts between parallel PRsConfirm tasks are truly independent before fanning out
Agent completes the wrong thingAlways use explicit acceptance criteria
Inconsistent style across agent PRsStrong shared AGENTS.md + copilot-instructions.md
Silent scope creepState constraints explicitly ("don't touch X")
